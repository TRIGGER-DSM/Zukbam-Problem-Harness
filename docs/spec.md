## 2. 파이프라인 구조

```
[1번 입력] 키워드 ──▶ 문제 생성 ────┐
                                    ▼
[2번 입력] 지문 ──────────────▶ 지문 검증 ──▶ TC 생성 ──┐
                                                        ▼
[3번 입력] 지문+TC ────────────────────────────────▶ TC 검증 ──▶ 결과
```

- **2번과 3번은 검증 모듈**이고, **1번은 그 앞에 붙는 생성 단계**다.
- 1번이 만든 문제는 2·3번 검증을 반드시 거친다. 1번만 따로 돌면 아무도 검증하지 않은 문제가 나온다.
- 2번 입력도 TC 생성을 거쳐 3번 검증으로 이어진다.

### 1번 — 문제가 없을 때 처음부터 생성 (`generate`)
- 입력: 문제풀이 방식(DP, greedy 등) + 키워드(충전기, 개미 등) + 난이도(예: 백준 실버 3, 골드 5)
- 제약 조건과 TC는 AI가 정하고 검증한다. 누적합처럼 풀이를 강제할 조건이 필요할 때만 조건을 지정한다.
- 출력: 해당 키워드에 맞는 문제
- 계획: 인터넷에 올라온 실제 문제들을 분석한 뒤 만든다.
- 순서: 결과를 검증할 2·3번이 먼저 있어야 의미가 있으므로 마지막에 붙인다.

### 2번 — 사용자가 지문만 줄 때 (`review` → `testgen`)
- 목적: 지문의 논리적 오류 발견, 지문 수정 돕기
- 계획: 논리 오류를 찾는 방법론과 테스트 방법을 리서치한 뒤 만든다.
- 방법: 지문만으로는 "정답"이라는 기준이 없다. **서로 독립적인 풀이 두 개(효율 풀이 + brute-force)**를 만들어 예제와 랜덤 입력으로 대조한다. 결과가 갈리는 지점이 지문이 모호하거나 모순인 곳이다.
- 지적은 **[수정]**(오탈자·형식, 알아서 고침)과 **[질문]**("N=0이 가능한가?" 같은 출제 의도, 출제자에게 물음)으로 나눈다. 반복은 최대 3회.

### 3번 — 지문 + 테스트케이스를 함께 줄 때 (`testcheck`)
- A. TC 자체가 맞는지: validator로 `.in`의 제약 위반을 찾고, 정답 풀이 출력과 `.out`을 비교한다.
- B. TC가 충분히 강한지: 흔한 실수를 넣은 오답 풀이(wrong-solver)를 돌려 TC가 잡는지 본다.
- 사용자가 준 `.out`과 우리 정답이 다르면 어느 쪽이 맞는지 AI가 정하지 않는다. 결과가 갈리는 가장 작은 TC와 양쪽 출력을 보여주고 출제자에게 묻는다.
- 계획: B의 세부 방법은 리서치 후 채운다.

## 3. 설계상 유의점

1. **공통 형식을 먼저 정한다.** 문제 패키지(지문, 제약, 정답 코드, TC 폴더 구조)를 먼저 정해야 1→2→3이 이어진다.
2. **AI가 쓴 정답 출력을 그대로 믿지 않는다.** `.out`은 정답 코드를 실제로 실행해서 만든다.
3. **검증 스크립트는 재사용 가능하게 만든다.** 나중에 백엔드 기능으로 옮길 때 외부 프로세스로 호출해 그대로 쓴다.
4. **정답 코드가 틀릴 위험은 여러 겹으로 막는다.**
   1. 서로 모르는 풀이 두 개를 대조한다 (핵심). 정답 풀이와, blind-solver가 지문만 보고 쓴 brute-force를 작은 랜덤 입력 수백~수천 개로 대조한다. 다르면 스크립트가 결과가 갈리는 가장 작은 입력을 찾아 보여준다.
   2. 두 풀이가 지문을 똑같이 잘못 읽으면 대조로 못 잡는다. 그래서 지문의 예제 입출력과 반드시 일치해야 하고, review에서 "다르게 읽을 수 있는 문장"을 따로 본다. 두 풀이가 자주 엇갈리면 지문이 모호하다는 신호로 본다.
   3. brute-force가 못 도는 큰 입력은 정답 풀이 혼자 돈다. 작은 입력에서 충분히 일치한 것을 근거로 삼고, 시간 제한 안에 도는지는 따로 잰다. 필요하면 다른 방법으로 짠 효율 풀이를 하나 더 둔다(선택).
   4. 무한 루프·런타임 에러·메모리 초과는 스크립트가 정해진 문구(예: `시간 초과: 7.in`)로 보고한다.
   5. 100% 보장은 안 되므로 마지막에 사람이 검토한다. 끝 보고에 "몇 개 입력으로 대조했는지, 갈린 적이 있었는지"를 적는다.

## 4. harness 구조 (제안, 사용자 동의)

portfolio-harness에서 가져오는 것: 짧은 진입 CLAUDE.md, 진입 스킬 하나(start), 원칙·결정 문서 분리, 작성 과정을 모르는 독립 서브에이전트, 결정적 스크립트, [수정]/[질문] 루프, state.md 이어하기, 스크립트 회귀 테스트.
가져오지 않는 것: Codex 동기화, Discord 전송 훅, 디자인 단계.

```
Zukbam-problem-harness/
├─ CLAUDE.md                  진입 지시문 (짧게)
├─ DEVELOPMENT.md             harness 자체를 고칠 때의 규칙
├─ rules/
│  ├─ principles.md           문제 품질 원칙
│  └─ decisions.md            구조 결정 기록
├─ .claude/
│  ├─ skills/
│  │  ├─ start/               진입점: 입력 판별 → 1/2/3 분기, 진행 기록, 끝 보고
│  │  ├─ generate/            1번: 키워드 → 지문+제약          (실제 문제 분석 뒤)
│  │  ├─ statement-review/    2번: 지문 논리 검증·수정 돕기    (방법론 리서치 뒤)
│  │  ├─ testgen/             TC 생성: 생성기 → validator → 정답 실행 → .out
│  │  └─ testcheck/           3번: (A) TC가 맞는지 + (B) TC가 충분히 강한지
│  │     └─ scripts/          run / compare / validate / stress
│  └─ agents/
│     ├─ blind-solver.md      지문만 보고 독립적으로 풀이 작성
│     └─ wrong-solver.md      흔한 실수를 넣은 오답 풀이 작성 → TC가 잡는지 측정
├─ problems/<문제-슬러그>/    결과물 (git 제외)
└─ tests/run_tests.py

start ─┬─ 키워드   → generate ─┐
       ├─ 지문     ──────────── review ─→ testgen ─┐
       └─ 지문+TC  ──────────────────────────────── testcheck ─→ 끝 보고
```

만드는 순서:
1. 뼈대: CLAUDE.md, rules, start, 실행·비교 스크립트, 문제 패키지 형식. 리서치 없이 만들 수 있다.
2. testgen + testcheck(A): 방법이 이미 정해져 있다.
3. review(2번): 리서치 결과로 채운다.
4. testcheck(B): 리서치 결과로 채운다.
5. generate(1번): 실제 문제 분석 뒤 만든다.

리서치가 필요한 스킬은 처음엔 빈 상태로 두고, 리서치가 끝날 때마다 하나씩 채운다.

### 사용자
> claude code에게 harness를 주는걸로 설계를 할거고, 지금 BE랑은 별개야. 프로젝트가 무엇인지 알게 하기 쉽게 하기 위해 여기서 실행했어.

이해한 내용을 확인해 주세요. 맞다면 이 내용을 설계의 전제로 삼을게요.

- **harness 구성**: Claude Code가 읽는 지침(CLAUDE.md/skill), 작업 절차, 그리고 Claude가 호출하는 **검증 스크립트**. 결국 Claude가 생성과 수정을 맡고, 정답 코드를 실행해 `.out`을 만들고 brute-force와 대조하는 판정은 스크립트가 결정적으로 내리는 구조예요. 앞서 C안으로 말씀드린 방식을 Claude Code 안에 넣는 거라, "Claude Code에 harness를 준다"는 말씀과 같은 방향이라고 봤어요.

- **위치(따로 묻지 않고 기본값으로 처리)**: BE 레포에 섞지 않고 별도 디렉터리나 레포에 둡니다. 설계 문서도 거기에 쓸게요. 원하는 경로가 있으면 알려주세요.

> 운영자(또는 선생님)가 harness를 실행할 때 **무엇을 입력으로 주나요?**
> - **A. 최소 입력**: 알고리즘 주제와 난이도만 (예: "BFS, 중급"). 지문 소재와 제약 조건은 AI가 정함
> - **B. 상세 입력**: 주제, 난이도, 입력 크기 제한, 지문 소재/스토리, 시간 제한까지 지정
> - **C. 기존 문제 변형**: 직접 만든 문제나 참고 문제를 주면 비슷한 유형으로 새 문제를 만듦
> - **D. 여러 개 한꺼번에**: 위 입력을 목록으로 주면 N개를 연달아 생성

### 사용자
> 일단 과정을 정해야할거같은데, 여러 경우의 수가 있어.
> 1번은 문제도 없어서 문제를 처음부터 생성해야 할떄. 이때는 내 생각은 코테에서 문제풀이방식(DP, greedy, 등등..) 이랑 여러 키워드(충전기, 개미....) 이런걸 던져주면 그 키워드에 해당되는 문제를 만들어주는거야. 이 문제 생성은 지금 바로 짜는게 아니라 실제 인터넷에 올라와있는 문제들을 분석해서 harness를 만들거니까 대충 이런걸 만들거다. 라고 생각하면 돼. 이후에 2번으로 넘어갈꺼야.
> 2번은 사용자가 문제만 전달 해주는거야. 여기서는 문제에서 논리적 오류가 있는지 확인할거야. 혹은 문제 수정을 돕거나. 여기서는 문제의 논리적으로 오류를 발견해야 해서 관련 방법론, 테스트 방법을 찾아서 harness를 개발할거야.
> 3번은 테스트케이스까지 같이 전달해주는거야. 여기서는 문제의 테스트케이스를 만들고 여기서 통과하는 오류값이 있는지 확인할거야. 여기서 사용할 테스트 방법을 찾아보고, 그중에서 맞는걸 골라서 harness를 생성할 예정이야.

### Claude
구조는 좋아요. 입력이 얼마나 갖춰졌는지(키워드만 / 지문 / 지문+TC)로 나눈 건 실제 쓰임새와 잘 맞아요. 다만 세 가지를 **따로 떨어진 기능**으로 보기보다 **하나의 파이프라인에서 시작점만 다른 것**으로 보면 구조가 훨씬 단순해져요.

```
[1번 입력] 키워드 ──▶ 문제 생성 ─┐
[2번 입력] 지문 ───────────────▶ 지문 검증 ──▶ TC 생성 ─┐
[3번 입력] 지문+TC ─────────────────────────────────▶ TC 검증 ──▶ 결과
```

- 1번이 만든 문제는 결국 2번과 3번의 검증을 거쳐야 믿을 수 있어요. 1번만 따로 있으면 AI가 만든 문제를 아무도 검증하지 않게 돼요.
- 2번 입력도 TC가 없으니 TC를 만들고 나면 3번 검증으로 이어져요.
- 그래서 **2번과 3번은 "검증 모듈"**이고, **1번은 그 앞에 붙는 "생성 단계"**예요. 세 harness가 따로 있는 게 아니라 같은 모듈을 공유하게 돼요.

**짚어둘 점이 두 가지 있어요.**

1. **공통 형식을 먼저 정해야 해요.** 각 단계를 따로 리서치하면 단계별로 결과물 형식이 달라지기 쉬워요. 문제 패키지(지문, 제약, 정답 코드, TC 폴더 구조)를 먼저 정해두면 1→2→3이 자연스럽게 연결돼요.
2. **2번에는 "정답"이 없어요.** 지문만 받으면 논리 오류를 판단할 기준이 없어요. 보통은 서로 독립적인 풀이 두 개(효율적인 풀이와 brute-force)를 만들어 예제와 랜덤 입력으로 대조해요. 결과가 갈리는 지점이 곧 지문이 모호하거나 모순인 곳이에요. 그래서 2번에서도 결국 풀이 코드를 만들게 되고, 이건 3번과 겹쳐요. 리서치할 때 이 부분을 염두에 두시면 좋아요.
